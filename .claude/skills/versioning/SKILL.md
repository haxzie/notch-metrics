# Changesets

```bash
pnpm changeset        # tick the packages, pick a bump, write one sentence
```

The sentence goes into the release notes verbatim. Write it for somebody
deciding whether to update, not for the person reviewing the diff.

## Tick `@notch/mac` for any Mac change

A Swift app depends on nothing in this workspace, so `updateInternalDependencies`
will never bump it the way a shared package would bump its dependents. **You
have to name it.**

CI enforces this — the `changeset-guard` job fails a PR that touches
`apps/mac/Kit/Sources/` or `apps/mac/App/` without a changeset naming
`@notch/mac`. The scope is deliberate: editing `project.yml` or a test needs no
user-facing changelog entry.

## Do not tick `@notch/web` or `@notch/api`

They are in `ignore`. Both are _deployed_, not _released_: no version a user can
observe, no install step, no rollback a version number helps with.

## Bumps

- **patch** — a fix, or anything a user would not notice.
- **minor** — anything a user _would_ notice.
- **major** — a conversation, not a checkbox.

## Never hand-edit

- a `version` field in any `package.json`
- any `CHANGELOG.md`
- `apps/mac/Config/Version.xcconfig`

The last one is generated by `scripts/sync-mac-version.mjs` from
`apps/mac/package.json` and committed so a fresh clone can run `xcodebuild`
with no Node step. `pnpm run version` regenerates it as part of the Version
Packages PR, and CI checks it with `--check`.

## What happens after merge

`version.yml` opens a "Version packages" PR. Merging _that_ publishes
`@notch/mcp` to npm and pushes an annotated `mac-v<version>` tag, which is what
starts a Mac release. See the `release` skill.
